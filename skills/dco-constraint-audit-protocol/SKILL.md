# 高约束审计指令协议

## 为什么有效

高压、确定性的命令式约束能提升表现，机制不是「语气更凶」，而是**礼貌性冗余被消除后语义噪音下降，注意力集中到边界条件上**。所以合规化平替只需要复现这个机制：确定性、可判定、无软词。

## 触发条件

适用：长程审计、法规与合规核对、需要可复现的严肃产出、长对话中约束已开始漂移。

不适用：创意写作、开放讨论、需要用户参与共创的场合。过度约束会压缩探索空间。

## 三件套

### 一、场景定义

把运行环境声明为零容错的系统底层架构或审计环境，并说明失败的后果类型。场景定义决定模型对错误的默认容忍度。

### 二、硬性约束

写成可判定的禁止项，禁止出现「尽量」「建议」「视情况」这类软词。示例：

```text
- 禁止使用省略号、占位符、TODO 代替任何推导步骤
- 禁止跳步：每一步必须显式指向上一步的产出
- 禁止在未完成自检前输出最终结论
- 违反任一条即判定为执行失败，输出作废
```

每条约束都要能被自动判定违反与否。判定不了的约束等于没有约束。

### 三、阶段化交付

按依赖图谱展开 → 逐步显式追踪 → 收敛核验三阶段闭环交付，每阶段设通过条件，未通过不得进入下一阶段。

## 注入位置

| 位置 | 内容 | 原因 |
| --- | --- | --- |
| 系统提示词开头 | 完整铁律 | 建立初始边界 |
| 系统提示词末尾 | 同份铁律（精简版） | 抵抗长上下文中段迷失 |
| 按需动态注入 | 百行以上规则模块 | 避免被淹没在超长历史中 |

百行以上的结构化模块规则，**不要长期泡在对话历史里**，改为在相关任务触发时动态注入。

## 反模式

- 用攻击性词汇代替边界条件（提高的是服从表演，不是准确率）。
- 约束重复但互相冲突，导致模型在矛盾中选择最省力路径。
- 只写「要严格」却不写怎么判定严格。
- 把所有规则堆在对话中段，首尾无锚点。

## 自检清单

- [ ] 每组约束可自动判定违反与否
- [ ] 提示词首尾各含一份完整铁律
- [ ] 无软词、无礼貌性冗余、无语义噪音
- [ ] 三阶段各有通过条件，且阶段间有门控
- [ ] 长规则模块走动态注入而非常驻历史
